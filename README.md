# Cloud-Native Platform for Edge-Delivered Static Hosting

## 1. The Problem and Domain

Modern static website hosting (such as Single Page Applications built with Vite) is often handled negligently in the cloud, resulting in storage buckets directly exposed to the internet, unpredictable costs caused by bot scans against nonexistent routes, and a complete lack of observability and security.

The goal of this project is not to explore front-end business rules, but rather to serve as a **Platform and Cloud Engineering case study**. The focus is on architecting, in an automated, declarative (IaC), and idempotent manner, a secure Edge-Delivered perimeter, ensuring complete storage isolation, intelligent routing, and strict cost-control principles (FinOps) through the AWS ecosystem (emulated and tested via LocalStack).

## 2. Application Architecture and Patterns

The request flow was designed around a "Serverless Edge-Delivered" architecture, where the infrastructure responds to requests as close as possible to the end user:

* **The Intelligent Entry Point (DNS):** Name resolution is orchestrated by **Amazon Route 53**, using Alias (`A`/`AAAA`) records that dynamically point to the CDN's global network, natively supporting IPv4 and IPv6 traffic with high availability.

* **Perimeter Security and Inspection (Layer 7):** Before any file is served, the request passes through **AWS WAFv2**. It acts as a shield against common web attacks, implementing rate limiting and blocking malicious traffic before it generates cloud bandwidth costs.

* **Edge Delivery and Routing:** **AWS CloudFront** is the brain of the operation. It manages global caching, handles TLS termination, injects strict HTTP security headers (e.g., Anti-Clickjacking and XSS protection), and intercepts storage errors, routing missing requests to the SPA or to physical error pages (404).

* **Storage Vault (Zero-Trust Origin):** The compiled artifacts (HTML/CSS/JS) reside in **Amazon S3**. The bucket is configured with absolute public access blocking and has no direct internet access routes. Read access occurs exclusively through authentication via **Origin Access Control (OAC)**, using `sigv4` cryptographic signatures generated by the CDN itself.

## 3. Security, Resilience, and Observability Engineering

Operating public infrastructure requires defensive mechanisms coupled to the request lifecycle to prevent data leakage and denial-of-service attacks:

| Component / Scenario         | Technical Risk                                                                                                   | Protection Mechanism          | Implementation Strategy                                                                                                                                                                                                       |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------------- | ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Origin Exposure**          | Direct access to files in the S3 bucket, bypassing the cache and WAF security rules.                             | Zero-Trust Origin with OAC    | Strict application of `block_public_acls` on S3. The bucket rejects public reads, accepting only authenticated requests from the CloudFront Service Principal associated with the account's distribution.                     |
| **Hybrid SPA Routing**       | In SPAs, client-side routes (e.g., `/dashboard`) generate an S3 error, negatively affecting UX and SEO crawling. | Edge Interception and Rewrite | Use of `custom_error_response` in CloudFront: `403` errors are mapped back to the application (`/index.html` with HTTP 200), while `404` errors gracefully serve a physical fallback page (`/404.html` with a true HTTP 404). |
| **DDoS and Origin Scrapers** | Multiple malicious requests generating massive direct GET/read costs and outbound traffic.                       | Rate Limiting & TTL Shielding | AWS WAF blocks abusive IPs (e.g., >2000 req/5min). If traffic fails at S3, CloudFront caches the error for 3600s, preventing the attack from reaching the bucket again.                                                       |
| **Blind Observability**      | Origin downtime or attack spikes going unnoticed.                                                                | Proactive Alerts (CloudWatch) | Provisioning alarms monitoring the `5xxErrorRate` metric in CloudFront and request spikes in the WAF `BlockedRequests` metric.                                                                                                |

## 4. Architectural Decisions and FinOps Approach

The choice of components and modules focuses on maximum security combined with cost predictability:

* **Infrastructure Feature Toggles (Zero Base Cost):** AWS WAF has fixed monthly costs (~$5) independent of usage. To align the project with FinOps practices, the WAF module was implemented with conditionals (`count = var.enable_waf ? 1 : 0`). This allows Development and Testing environments to be deployed at an effective **zero cost** (Scale to Zero for S3/CloudFront), enabling the perimeter shield only in Production through variables, without changing the source code.

* **Standardized Tags (DRY):** The infrastructure adopts centralized global tag injection (`default_tags` in the Provider) and local merging (`merge(local.common_tags)`), ensuring strict governance and cost control in *AWS Billing* without requiring manual code repetition.

* **Early Validation (Fail-Fast):** Regular Expressions (`regex`) within `validation {}` blocks prevent Terraform execution when developers provide invalid patterns (e.g., illegal S3 bucket naming conventions or unsafe WAF limits), preserving CI/CD execution time and avoiding unnecessary AWS API calls.

## 5. Infrastructure as Code (IaC)

Environment provisioning and lifecycle management are handled declaratively and modularly through **Terraform**. The project adopts Inversion of Control through the **Pure Modules** pattern and an orchestrating **Root Module**:

* **Pure Modules (****`/infra/modules/*`****):** Components (`storage`, `cdn`, `waf`, `dns`, `monitoring`) are stateless and have no knowledge of other modules. They receive strictly typed dependencies (`object({})`) through their variables. The S3 module, for example, can be reused in other company contexts (such as logs or backups) without requiring refactoring, as it is not natively coupled to a CDN.

* **Glue Code (****`/infra/environments/dev/main.tf`****):** Acts as the conductor. It is responsible for instantiating the modules, extracting an *output* from one (e.g., the Web ACL ARN), and injecting it as an *input* into another (e.g., the CloudFront distribution configuration), ensuring a linear and deterministic dependency graph that eliminates Terraform execution failures.

## 6. Known Limitations and Trade-offs

* **Emulation Boundaries (LocalStack):** The environment includes CI/CD that performs end-to-end tests against **LocalStack Pro**. However, this emulator cannot perfectly reproduce the physical behavior of AWS networking, such as geographic latency, global propagation of Route 53/CloudFront, or the TLS protocol resilience of the real infrastructure.

* **Hybrid Rendering and SEO:** Although intercepting and serving `/404.html` with the correct response code improves crawling, the current application is entirely static (Client-Side SPA). The initial `index.html` is delivered without rendered content to search engines. For critical organic indexing (SEO), this infrastructure would need to evolve to integrate edge computing (using **Lambda@Edge** or **CloudFront Functions** for metadata injection) or adopt an SSR framework.
